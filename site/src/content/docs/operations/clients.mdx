The dependable compatibility contract is capability-based, not a hard-coded client version
matrix. Client releases change independently, so verify the features you need in the current
client rather than relying on an old “yes/no” table.

## Local stdio contract

A client can use discord-mcp's core surface when it can:

1. start a local process as an MCP server;
2. communicate with it over stdio;
3. pass `DISCORD_TOKEN` and other environment variables; and
4. list and call MCP tools.

That contract is enough for the 192 Discord-operation tools. The separate
Emoji.gg inspiration discovery tool is optional; resources, subscriptions, and
sampling are optional extensions with narrower use cases.

## Remote HTTP contract

A remote client instead needs Streamable HTTP MCP support, a publicly reachable
HTTPS `/mcp` endpoint, and a way to send the configured bearer credential.
This covers the OpenAI Responses API and Codex. Remote HTTP negotiates MCP
`2026-07-28` and preserves stateless 2025-era compatibility; neither path uses
MCP session state. It does not support Discord Gateway subscriptions. See
[OpenAI remote MCP](/discord-mcp/operations/openai/) for the shared-bot
security model and setup.

## Feature requirements

| discord-mcp feature | Client capability | Behavior when absent |
|---|---|---|
| Discord tool catalog | `tools` | Core functionality is unavailable. |
| Components V2 schema/template catalog | `resources` list/read | Use the tool reference and builder tools instead. |
| Live Gateway notifications | resource subscriptions | The client cannot receive push updates; REST tools still work. |
| Intelligence tools | sampling | The tool returns a host-processing fallback payload rather than a completed LLM analysis. |
| Confirmation gate | none beyond tools | The `__confirm` contract is a tool argument; discord-mcp does not use MCP elicitation. |

<Aside type="caution">
The server currently advertises subscription support even when Gateway mode is not active.
Treat live subscriptions as experimental and verify an actual update end-to-end before building
a workflow around them.
</Aside>

If you did not install the CLI globally, the scoped one-off command is
`npx --yes @discord-mcp/cli@latest`. Do not substitute an unscoped package name.

## Verify instead of assuming

For every client and release:

1. Run `discord-mcp doctor --online` in a terminal with `DISCORD_TOKEN` set.
2. Restart the client and confirm `users_get_current` succeeds.
3. Confirm `channels_list` can discover a test channel.
4. If you need intelligence, run its smallest example and inspect whether the response is a
   completed result or a host-processing fallback.
5. If you need Gateway events, verify one real subscription update after starting with
   `--gateway`; do not infer support from the initialization capability alone.

## Server-side controls

- `ALLOWED_GUILDS` verifies direct and indirectly resolved Discord guild targets,
  and hides global writes whose guild cannot be proven before execution.
- `MCP_CATEGORIES` limits which tool categories are advertised and callable.
- `MCP_TOOL_SURFACE=progressive` advertises search plus risk-specific read,
  write, and destructive dispatchers instead of the full catalog; it does not
  expand `MCP_CATEGORIES` authorization.
- `MCP_DRY_RUN` affects only tools that declare the confirmation precondition.
- `OTEL_ENABLED` changes server-side observability, not the client capability contract.
