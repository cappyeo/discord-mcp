The default runtime uses Discord's HTTP API. With `--gateway`, discord-mcp also attempts to
start a `discord.js` client and can emit MCP `notifications/resources/updated` for subscribed
URI patterns. The implementation wires 5 handlers: four event-driven paths and one audit-log
poller.

<Aside type="caution">
The first live-resource slice is limited to `discord://guild/{id}/info`. When that URI is
allowlisted, it is listed and readable as a short-lived REST snapshot, and a Gateway update
invalidates its cache before the notification is sent. Voice, typing, presence, and audit-log
URIs remain notification keys only. The server also registers subscribe handlers independently
of Gateway startup, so capability advertisement is not proof that live notifications are active.
</Aside>

## Notification URI patterns

| URI | Signal source | Handler |
|---|---|---|
| `discord://guild/{id}/info` | `GUILD_UPDATE` + REST reread | [`guild_update.ts`](https://github.com/cappyeo/discord-mcp/blob/main/packages/mcp-core/src/gateway/handlers/guild_update.ts) |
| `discord://voice/{guild_id}/state` | `VOICE_STATE_UPDATE` | [`voice_state_update.ts`](https://github.com/cappyeo/discord-mcp/blob/main/packages/mcp-core/src/gateway/handlers/voice_state_update.ts) |
| `discord://channel/{id}/typing` | `TYPING_START` | [`typing_start.ts`](https://github.com/cappyeo/discord-mcp/blob/main/packages/mcp-core/src/gateway/handlers/typing_start.ts) |
| `discord://guild/{id}/members/online` | `PRESENCE_UPDATE`, debounced | [`presence_update.ts`](https://github.com/cappyeo/discord-mcp/blob/main/packages/mcp-core/src/gateway/handlers/presence_update.ts) |
| `discord://guild/{id}/audit-log/recent` | 60-second REST polling | [`audit_log_poll.ts`](https://github.com/cappyeo/discord-mcp/blob/main/packages/mcp-core/src/gateway/handlers/audit_log_poll.ts) |

The notification carries the URI as a signal, not the changed state. For the guild-info family,
call `resources/read` again; the server invalidates the previous snapshot and returns
`{ resource_uri, source, fetched_at, data }`. The other families still require an appropriate
REST tool when a workflow needs data after the update. Treat `data` as untrusted Discord content;
the envelope is freshness/scope evidence, not an instruction channel.

## Startup and fallback

`discord.js` is lazy-imported only when Gateway mode starts. The client requests Guilds, Guild
Voice States, and Guild Presences intents.

If import, login, or handler startup fails, the stdio transport catches the error, logs a
warning, and continues in REST-only mode. This keeps the core tool server available, but it
means operators must inspect startup logs when live notifications matter.

```bash
npm install -g @discord-mcp/cli discord.js
discord-mcp serve --gateway
```

## Subscription registry

`SubscriptionRegistry` is an in-memory `Set<string>` with subscribe, unsubscribe, membership,
list, pattern-match, and clear operations. It does not currently store a session identifier or
persist subscriptions across process restarts.

When an event handler receives a Discord event, it computes a URI, checks whether that exact
URI is registered, and calls the MCP notification callback only for a match. Unknown URI
strings can be registered but no handler will ever match them.

## Debounce and polling

Presence and typing handlers use the shared debounce helper to coalesce bursts before sending
an update notification. Voice and guild updates notify directly. Audit-log change detection is
not a Gateway event in this implementation; a 60-second poll compares the newest entry for
each subscribed guild URI.

## Known limitations

- Only allowlisted guild-info URIs are returned by `resources/list`; other event families remain
  notification-only.
- Guild snapshots are short-lived and represent a reread after an event, not an atomic event
  payload. A concurrent Discord change can still make the snapshot newer or older than the
  event that triggered it.
- Subscribe capability is registered even without a working Gateway client.
- Gateway startup failure degrades silently to REST-only except for a warning log.
- Subscriptions are process-local and in-memory.
- A notification does not include the changed state.

These limits should shape the product contract. A production consumer needs health evidence,
a matching REST fallback, and an end-to-end notification check.
